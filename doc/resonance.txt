1. Introduction                                    *resonance-introduction*

Resonance is a lightweight plugin manager for Neovim 0.13+ that wraps the
native |vim.pack| API with lazy-loading capabilities and a Terminal UI.

Key features:
- Native |vim.pack| integration (no external dependencies)
- Lazy loading via triggers: events, commands, filetypes, keymaps
- Automatic dependency resolution
- Build hooks with hash-based caching
- Terminal UI for plugin management (install, update, checkout, uninstall)
- DAG visualization of plugin dependencies
- Event replay for correct autocmd ordering
- Fallback mode when vim.pack is unavailable
- Sub-millisecond startup overhead

==============================================================================
2. Installation                                    *resonance-installation*

Requirements:
- Neovim 0.13+ (for |vim.pack|)
- Git

Using |vim.pack| (recommended):
    :lua vim.pack.add({{src='https://github.com/yourname/resonance.nvim'}})
    :packadd resonance.nvim

Manual installation:
    git clone https://github.com/yourname/resonance.nvim \
      ~/.local/share/nvim/site/pack/core/opt/resonance.nvim

Then add to your init.lua:
    require('resonance').setup()

3. Quick Start                                     *resonance-quick-start*

Basic setup in your init.lua:

    local resonance = require('resonance')
    resonance.setup()

    resonance.load({
      -- List of plugin specifications
      {
        src = 'https://github.com/neovim/nvim-lspconfig',
        event = {'BufReadPre', 'BufNewFile'},  -- Lazy load on opening a file
        dependencies = {'https://github.com/nvim-lua/plenary.nvim'},
        build = 'echo "building"',     -- Optional build command
      },
      {
        src = 'https://github.com/folke/which-key.nvim',
        event = 'VeryLazy',            -- Once the UI is up
      },
      {
        src = 'https://github.com/nvim-treesitter/nvim-treesitter',
        build = function(dir)          -- Function build hook
          -- The build can run before the plugin is loaded, so load it
          -- first or :TSUpdate does not exist yet.
          vim.cmd.packadd('nvim-treesitter')
          vim.cmd('TSUpdate')
        end,
      },
      {
        src = 'https://github.com/user/optional-plugin',
        cond = function() return vim.fn.executable('rg') == 1 end,  -- Load only if ripgrep exists
      },
      {
        src = 'https://github.com/user/eager-plugin',
        lazy = false,                  -- Eager load on VimEnter
      },
      {
        src = 'https://github.com/user/lazy-plugin',
        lazy = true,                   -- Lazy load on VeryLazy
      },
    })

    -- Open UI with :Resonance or lua
    vim.keymap.set('n', '<leader>rp', function()
      resonance.open_ui()
    end)

`setup()` takes the UI options and `replay` (see |resonance-api-main|).
Plugin specifications go to `load()`. `User VeryLazy` fires on its own
once the UI is up, and the files opened before it are replayed for the
triggers registered then -- there is nothing else to call.

4. Configuration                                   *resonance-configuration*

The `resonance.load()` function accepts a list of plugin specifications.
Each spec is a table with the following fields:

Common fields:
    src (string)        Git repository URL (required)
    name (string)       Override plugin name (derived from URL if omitted)
    version (string)    Git tag/branch/commit to checkout
    event (string|table) Lazy load on autocmd event(s)
    cmd (string|table)  Lazy load on command(s)
    ft (string|table)   Lazy load on filetype(s)
    keys (table|function) Lazy load on keymap(s) or function returning keymaps
    dependencies (table) List of dependency plugin URLs
    build (string|function) Build command or function(dir)
    config (function)   Called after plugin loads (alias for setup)
    setup (function)    Called after plugin loads
    plugin (table)      Alternative spec format (lazy.nvim compatible)
    lazy (boolean)      false = eager (VimEnter), true = VeryLazy default
    cond (boolean|function) Conditional loading: a false result skips the
                        plugin (a function returning nil too)

Multiple plugins are registered with one `resonance.load()` call, as a
list:

    resonance.load({
      {src = '...', event = '...'},
      {src = '...', cmd = '...'},
    })

    -- A single plugin can be passed on its own
    resonance.load({src = '...', event = '...'})

4.1 Lazy Loading Triggers                          *resonance-triggers*

event - Load when autocmd fires:
    event = 'LspAttach'
    event = {'BufReadPost', 'BufNewFile'}
    event = {'BufReadPost', pattern = {'*.lua', '*.vim'}}  -- With a pattern
    event = 'VeryLazy'                       -- User VeryLazy
    event = 'User MasonLoaded'               -- any User event
    event = {'User', pattern = 'MasonLoaded'}  -- the same, native form
    event = {'InsertEnter', 'User MasonLoaded'}  -- mixed in a list
    event = {'InsertEnter', {event = 'BufEnter', pattern = '*.md'}}
                                       -- a pattern applies to its own event

    An unknown event name is reported with a notification and skipped.
    The valid events of the same spec, and every spec after it, still
    register.

cmd - Load when command is invoked:
    cmd = 'Neogit'
    cmd = {'Neogit', 'Git'}
    cmd = {name = 'Neogit', opts = {nargs = 0}}  -- With the command's own options

    A command with nargs = 0 takes no arguments, so no completion is
    attached to it. A completion set in opts is kept as given.

ft - Load when filetype is set:
    ft = 'lua'
    ft = {'lua', 'python'}

keys - Load when keymap is pressed:
    keys = {'<leader>g', '<leader>gg'}
    keys = {{'n', '<leader>g', func, {desc = 'Git'}}}  -- Full keymap spec
    keys = function() return {{'n', '<leader>g', func}} end  -- Function returning keymaps

    A key without an rhs means the plugin defines the mapping itself. The
    stub is removed once the plugin has loaded, and the plugin's own
    mapping is left in place. A key with an rhs keeps that rhs: the stub
    is replaced by the real mapping after the load.

cond - Conditionally load plugin:
    cond = true          -- Load (default)
    cond = false         -- Skip plugin entirely
    cond = function() return vim.fn.has('nvim-0.10') == 1 end  -- Conditional

lazy - Shorthand for common lazy-loading patterns:
    lazy = false         -- Eager load on VimEnter (no event/cmd/ft allowed)
    lazy = true          -- Lazy load on VeryLazy (User VeryLazy event)

`lazy = true` adds VeryLazy as an extra trigger: an explicit
event/cmd/keys/ft keeps working, and the plugin also loads on VeryLazy
if none of them fired first. It does not replace them.

`lazy = false` cannot be combined with `event`, `cmd` or `ft` -- it
means the plugin loads eagerly on VimEnter. `keys` is allowed, because a
keymap works after an eager load.

Triggers can be combined. Plugin loads on FIRST matching trigger.

A spec with no trigger and no `lazy` field loads eagerly on VimEnter, the
same as lazy = false. Useful for a plugin you just want installed and
pinned, with no trigger of its own.

`event` accepts a User event with its own pattern:
    event = 'VeryLazy'
    event = {'User', pattern = 'VeryLazy'}

4.2 Dependencies                                   *resonance-dependencies*

    dependencies = {'https://github.com/nvim-lua/plenary.nvim'}

Dependencies are loaded BEFORE the plugin. They support all trigger types.
Circular dependencies are detected and reported.

4.3 Build Commands                                 *resonance-build*

String command (runs in plugin directory):
    build = 'make' or build = './install.sh'

Function hook (receives plugin directory):
    build = function(dir)
      vim.system({'cargo', 'build', '--release'}, {cwd = dir})
    end

A function hook may return the object it started the work with. The build
is not marked as successful until that work has finished, so a hook that
runs `vim.system()` or returns a promise is waited for:
    build = function(dir)
      return vim.system({'cargo', 'build', '--release'}, {cwd = dir})
    end

Build runs automatically:
- On install (via PackChanged event). An install always builds, even if a
  marker from an earlier install is left over.
- On update (when git hash changes)
- Deleting a plugin (the UI's `dd`, |vim.pack.del()| or :packdel) removes
  its marker, so a reinstall builds again.
- Hash cached in the build marker to avoid rebuilds. The markers live in
  `stdpath('state') .. '/resonance/builds/'`, not in the plugin's own
  directory, so they never show up in its git working tree.

The commit is read from the plugin's git files, so the check spawns no
subprocesses.

The build verdict is the exit code, and nothing else. A build that exits 0
is a success even when stderr is not empty -- yarn, npm, cargo and make all
write warnings and progress to stderr on a successful build. The output of
both streams is captured and shown with a failure, so a swallowed error is
still visible.

                                                    *resonance-build-order*
The setup runs after the build has finished. A plugin is never set up
against a half-built tree -- a setup that expects the build's output (a
node_modules directory, a compiled native module) would otherwise fail.

- A plugin loaded by a command or a keymap waits for its build. The wait
  is bounded; if the build outlasts it, the setup is deferred and you are
  told the build is still running.
- A plugin loaded by an event, a filetype or an eager load does not wait.
  The editor is never blocked by a build it did not ask for, and the
  setup runs when the build finishes.

Only one build of a plugin runs at a time, across Neovim sessions too. A
session that finds another session building the plugin waits for it, and
skips the build if the other session already built that commit. A build
that runs longer than 10 minutes is killed and reported as failed.

A build that fails does not stop the plugin from being set up. The failure
is reported, and the setup runs anyway -- the plugin may still work without
the build's artifacts.

                                                    *resonance-build-config*
Build options go in the `build` section of |resonance.setup()|: >lua

    require('resonance').setup({
      build = {
        concurrency = 2,   -- build commands that run at once
        progress = true,   -- report builds as progress messages
      },
    })
<
`concurrency` limits the string build commands (`build = 'make'`) that run
at the same time; the rest queue for a free slot. Lua build hooks are not
counted: they run in the editor, and the work they start is their own. It
must be a positive integer, otherwise the default is used and you are
warned. A new value applies to the builds that start after it is set.

With `progress` on, the builds in flight are reported as one
|progress-message|, counted the way vim.pack counts an install: >

    Resonance:   0% Building (0/3) blink.cmp
    Resonance:  66% Building (2/3)
    Resonance: 100% Build done
<
The last update sums the batch up: "Build done", "Build failed" (every
build failed) or "Build failed partially". Which plugin built or failed,
and why, is in the notification sent for each build, which is sent
whether `progress` is on or not. A build that starts after a batch ended
starts a new count.

Neovim shows the message in the message area, and any plugin that listens
to the |Progress| event can show it too: filter on
`ev.data.source == 'resonance'`. `ev.data.status` is "running", then
"success" or "failed" (any build failed); `ev.data.data` holds `done`,
`total`, `failed`, and `plugin` on the update that starts a build.

4.4 Version Pinning                                *resonance-version*

Pin to specific tag, branch, or commit:
    version = 'v1.0.0'      -- Tag
    version = 'main'        -- Branch
    version = 'abc1234'     -- Commit hash

In a spec with several plugins, pin each one in its own table:
    plugin = {
      { 'https://github.com/user/a', version = 'v1.0.0' },
      'https://github.com/user/b',
    }
    plugin = { 'https://github.com/user/a', version = 'v1.0.0' }  -- one plugin
    plugin = { 'https://github.com/user/a', 'https://github.com/user/b' }  -- two

A spec must name a plugin (`src`, `url`, or a URL as its first element).
One without is reported and skipped.

5. User Interface                                  *resonance-ui*

Open UI:
    :lua require('resonance').open_ui()
    :Resonance  (user command created by setup)

The UI shows all installed plugins with status, triggers, and metadata.

The UI options are set through `resonance.setup()`:

    resonance.setup({
      ui = {
        border = 'rounded',      -- 'single', 'double', 'rounded', 'none'
        title = ' Resonance ',
        width = 0.65,            -- fraction of the editor width
        height = 0.75,           -- fraction of the editor height
        backdrop = 60,           -- 0-100, dim the editor behind the UI
      },
    })

5.1 Key Mappings                                   *resonance-ui-keys*

In the Resonance UI buffer:

    <CR>         Toggle plugin details (expanded view)
    r            Check for updates (network)
    u            Update plugin under cursor
    U            Update all plugins with pending updates
    s            Skip update for plugin under cursor
    c            Checkout branch/tag/commit (prompts for target)
    dd           Uninstall plugin under cursor
    S            Search the source of all plugins (grep in the pack dir)
    D            Open the pack directory in an explorer
    C            Run native vim.pack.update (offline)
    A            Toggle DAG view (dependency graph)
    q / <Esc>    Close UI

5.2 Plugin Details                                 *resonance-ui-details*

Press <CR> on a plugin to expand details showing:
- Load status (active/inactive)
- Git branches (the remote branches, default branch first)
- Git tags (latest 5)
- Installation path
- Source URL
- Current commit hash

The load time is shown on the plugin's own row, not in the details.

5.3 Custom Icons                                  *resonance-ui-icons*

The glyphs used for each plugin state can be changed via the `ui.icons`
option. Each key is independent, so unspecified keys keep their defaults.

    loaded (string)      Glyph for a loaded plugin        (default: '●')
    not_loaded (string)  Glyph for an unloaded plugin      (default: '○')
    disabled (string)    Glyph for a cond-disabled plugin  (default: Nerd Font)

Example: >

    resonance.setup({
      ui = {
        icons = {
          loaded = '✓',
          not_loaded = '✗',
          disabled = '',
        },
      },
    })

Note: The default `disabled` glyph is a Nerd Font private-use codepoint
(U+F057). If it renders as a blank box, set it to a codepoint your font
actually has.

6. API Reference                                   *resonance-api*

6.1 Main Functions                                 *resonance-api-main*

    resonance.setup([config])
        Initialize Resonance: creates the :Resonance command, merges the
        options, and arms `User VeryLazy`.
        config: optional table:
            ui      the UI options (see |resonance-ui|)
            replay  replay the read events for the open files right after
                    VeryLazy (default: true). Read when VeryLazy fires, so
                    it can be set after load() has already been called.
        Returns: nothing

    resonance.open_ui()
        Open the Terminal UI.
        Returns: nothing

    resonance.load(config)
        Register one plugin specification, or a list of them.
        Supports all config fields including lazy, cond, keys as function.
        Returns: nothing

    resonance.stats()
        Plugin statistics.
        Returns: {count, loaded, startuptime, times}

        count         Total number of plugins managed
        loaded        Plugins currently loaded
        startuptime   Startup time in milliseconds
        times         Table of plugin_name -> load_time_ms

        `startuptime` is a one-shot measurement, latched once and never
        changed afterwards. It is latched at UIEnter (VimEnter when there
        is no UI), or by the first stats() call if that comes first. The
        counts are read live on every call, because a plugin can load at
        any point.

    resonance.trigger_verylazy()
        Optional: setup() and load() already arm `User VeryLazy`. Kept so
        configs that call it keep working; calling it as well fires
        VeryLazy only once.
        Returns: nothing

    resonance.has_fired(event, buf)
        Whether an event has already fired for a buffer.
        event: event name, e.g. "BufReadPost"
        buf: buffer number
        Returns: boolean

        Use this to avoid replaying an event that already ran. Firing an
        event twice makes every handler for it run twice.

    resonance.replay_for_buffer(buf)
        Replay the read events a buffer has already missed.
        buf: buffer number
        Returns: table of the events that were replayed

        Fires each read event once per trigger group that has not yet run
        for the buffer. A handler is therefore never invoked twice for the
        same read, while a trigger registered after the event already fired
        still gets its chance to load.

        Events still pending for the current read are left alone: Neovim
        fires them naturally. An invalid buffer id is ignored.

        Resonance already runs it for every open file right after
        VeryLazy (see `replay` in resonance.setup()), so a config does not
        need to. Call it yourself only for a buffer you open later from
        your own code. Calling it twice is safe: a group that already ran
        is not fired again.
6.2 Loader Module                                  *resonance-api-loader*

    local loader = require('resonance.loader')

    loader.load(config)
        Load plugin specification with triggers.

    loader.get_plugin_dir(name)
        Get filesystem path for installed plugin.
        Returns: string path or nil

    loader.has_fired(event, buf)
        Whether an event has already fired for a buffer.
        See |resonance-api-main| for resonance.has_fired().
        Returns: boolean

    loader.replay_for_buffer(buf)
        Replay the read events a buffer has already missed.
        See |resonance-api-main| for resonance.replay_for_buffer().
        Returns: table of the events that were replayed

    loader.run_build(name, dir, build_task, curr_hash, on_done)
        Execute build command for plugin.
        build_task: string command or function(dir)
        curr_hash: current git commit hash
        on_done: optional callback, called with (ok, err) once the build
            settles
        Returns: nothing (async)

    loader.check_and_build(name, dir, build_task)
        Check git hash and run build if changed.
        Returns: nothing (async)

    loader.mark_build_success(name, hash)
        Write build hash to the build marker for a plugin. The markers live
        in stdpath('state') .. '/resonance/builds/', so they never appear
        in a plugin's own git working tree.

    loader.setup_packchanged_autocmd(get_plugin_dir_fn)
        Register PackChanged autocmd for automatic builds.

    loader.get_dag_data()
        Returns: nodes, edges tables for dependency graph.

    loader.get_replay_info()
        Returns: event replay information for loaded plugins.

    loader._get_event_chain_internal(event, buf, data)
        Get autocmd chain for event replay.

    loader.build_hooks
        Table of plugin_name -> build_task (string|function)

    loader.plugin_triggers
        Table of plugin_name -> trigger string

    loader.specs
        Table of plugin_name -> a copy of the spec (the user's table is
        not modified)

6.3 Builds Module                                  *resonance-api-builds*

    local builds = require('resonance.builds')

    The build tracker. It holds the state of the builds and answers the
    queries; the loader keeps the mechanics. The module can be required
    on its own -- it does not pull in the loader.

    builds.status(name)
        The state of one build.
        Returns: {state = 'pending' or 'running' or 'ok' or 'failed',
                  started_at = hrtime, elapsed = ms,
                  error = string|nil, output_tail = string|nil,
                  pid = number|nil} or nil when there is no such build

    builds.wait(name, timeout_ms)
        Pump the event loop until the build settles. The default timeout
        is 30 seconds.
        Returns: boolean ok, string|nil err
        Note: a failure, a timeout and an interrupt (CTRL-C) all report
        ok=false. Ask builds.status() which it was -- a failed build is
        over; after a timeout or an interrupt the build is still running.

    builds.is_building(name)
        Whether a build for this plugin is pending or running.
        Returns: boolean

    builds.is_running(name)
        Whether the build for this plugin is running (not just pending).
        Returns: boolean

    builds.running()
        The names of the plugins whose build is running.
        Returns: table of plugin names

    builds.is_busy()
        Whether any build is running.
        Returns: boolean

    builds.HARD_TIMEOUT_MS
        How long a build may run before it is killed (10 minutes).

    builds.on_complete(name, fn)
        Call fn(ok, err) once when the build settles. The callback runs
        immediately if the build has already settled.

    builds.forget(name)
        Drop a finished build's state.

    builds.acquire_lock(name, pid)
        Take the cross-session lock for a plugin, so a second Neovim
        session does not build it at the same time.
        Returns: boolean acquired

    builds.holds_lock(name)
        Whether this session holds the lock for a plugin.
        Returns: boolean

    builds.release_lock(name)
        Release the cross-session lock for a plugin.

    builds.stale_locks()
        The locks whose process is gone. A session that was killed leaves
        its lock behind; the next session may then rebuild the plugin,
        because the build's artifacts are cheap to reproduce.
        Returns: table of plugin names

6.4 Scanner Module                                 *resonance-api-scanner*

    local scanner = require('resonance.scanner')

    scanner.get_info([opts])
        Get plugin information.
        opts: {info = boolean, offline = boolean}
        info=false (default): fast, no branches/tags
        info=true: includes branches, tags, rev_to
        offline=true (default): use cached data
        Returns: {plugins = {name[], type[], path[], loaded[], disabled[],
                  trigger[], ...}, total, loaded, pack_dir, load_times}
        The plugins are parallel arrays indexed 1..total. Use `total`, not
        `#`, to iterate: some arrays (rev, rev_to) have holes.

    scanner.get_detailed_info()
        Alias for get_info({info=true, offline=false})

    scanner.load_times
        Table of plugin_name -> load_time_ms

6.5 UI Module                                      *resonance-api-ui*

    local ui = require('resonance.ui')
    local actions = require('resonance.ui.actions')
    local state = require('resonance.ui.state')
    local render = require('resonance.ui.render')

    ui.open(ui_config)
        Open the UI window.

    actions.check_updates_network()
        Fetch remote updates for all plugins (async).
        Returns: boolean -- true when this call started a check, false when
        a check was already running.

        The `r` key uses the return value to notify only once. While a check
        is in flight the key is inert, so holding it cannot stack
        notifications.

    actions.update_plugins(names)
        Update specified plugins via vim.pack.update.

    actions.checkout_plugin(name)
        Interactive git checkout for plugin.

    actions.uninstall_plugin(name)
        Remove plugin from disk.

    state.state
        Current UI state table (plugins, commits, updates, etc.)

7. Events                                          *resonance-events*

Autocmd events emitted:

    User  VeryLazy          Fired when the UI has become usable, so that
                           plugins which did not load yet can.

`User VeryLazy` is armed by `resonance.setup()` and `resonance.load()`
and fires once, at UIEnter (VimEnter when there is no UI). When Resonance
itself is loaded after startup, it fires right away. Right after the
VeryLazy handlers have run, the read events are replayed for the open
files. A spec with `lazy = true` uses VeryLazy as its trigger.

Event replay ensures autocmds fire in correct order for nested triggers.

==============================================================================
8. Fallback Mode                                   *resonance-fallback*

When |vim.pack| is unavailable, or disabled with `vim.pack = false` before
setup (`vim.pack = nil` does not work: the lazy loader brings the module
back on the next read):
- Filesystem scan of `pack/*/{start,opt}/*` used instead
- All lazy-loading triggers work
- UI shows plugins from filesystem
- Build hooks work
- Update, uninstall and the native review (`u`, `U`, `dd`, `C`) are
  unavailable; checkout (`c`) still works, it runs git directly

==============================================================================
9. Performance                                     *resonance-performance*

Benchmarks (Neovim 0.13+, 43 plugins):
- Startup overhead: ~0.9ms average
- UI open: ~12ms (fast path + async branches/tags)
- scanner.get_info(): ~1ms (offline, info=false)
- scanner.get_info({info=true}): ~300ms (fetches branches/tags)

Optimizations:
- Two-pass UI loading (commits first, branches/tags deferred)
- vim.pack.get() cache for plugin paths
- Batched pack.add() calls
- Hash-based build caching (markers under stdpath('state'))
