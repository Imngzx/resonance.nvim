## Item 0 — Report install failures instead of swallowing them

**Why:** the loader's install path is the one place where resonance wraps
`vim.pack` *incorrectly*. This is the single most important thing a package
manager wrapper must not get wrong, and it is a smaller change than any
other item here. **Do this first.**

### The defect

`loader/init.lua:336,344`:

```lua
pcall(pack_add_safe, pack_plugins, { confirm = false, load = false })
```

`vim.pack.add` *raises* on failure — it collects per-plugin errors and calls
`error()` with a combined message (`vim/pack.lua`, tail of `M.add`). The
`pcall` discards both the error and the return value. Nothing downstream
inspects the result.

The second failure is subtler: **`:packadd` reports success for a plugin
that was never installed.**

```text
$ nvim --headless -c "packadd never-existed-probe"
packadd missing plugin: ok=true
is directory present = 0
```

So the wrapper cannot use `packadd` to detect failure either.

### Measured failure chain

Load a plugin whose `src` does not resolve:

```text
vim.pack.add ok=false
err=... error: unable to read askpass response
```

Through resonance's path:

```text
trigger ok=true
SETUP RAN                                  ← never printed
plugin_state.loaded = nil
replay_done = true
trigger still registered = false
DONE (no second install attempt = no output above)
```

| Step | Observed | Should be |
|------|----------|-----------|
| 1 | `vim.pack.add` raises | — |
| 2 | error swallowed by bare `pcall` | error surfaced to the user |
| 3 | `packadd` runs on a missing plugin, returns `ok=true` | install verified before `packadd` |
| 4 | `state.replay_done = true` set anyway | not set on failure |
| 5 | trigger consumed (`once=true`), **never retried** | trigger retried or failure reported |
| 6 | no error, no notification, no log | user is told |

The end state is a plugin that silently never loads and never loads again.

### Change

- `loader/init.lua:344` — capture the result:

  ```lua
  local ok, err = pack_add_safe(pack_plugins, { confirm = false, load = false })
  if not ok then
    utils.notify('Install failed: ' .. tostring(err), vim_log_levels.ERROR)
    return
  end
  ```

- `loader/init.lua:336` — same treatment for the dependency path.
- **Verify the install actually landed before `packadd`.** `packadd` lies, so
  check the plugin directory exists (the loader already has
  `get_plugin_dir`) before running `packadd`. A missing directory after a
  successful `pack.add` means the install did not produce a plugin.
- **Do not set `state.replay_done` on failure**, and do not consume the
  trigger. A failed install should be retryable on the next trigger.
- Report the failing plugin **name** in the notification, not just the raw
  error — the raw `vim.pack` message is a multi-line blob.

#### Contrast: the rest of the codebase already does this

| Site | Handling |
|------|----------|
| `scanner.lua:126` | `pcall(pack.get, ...)` then falls back to a filesystem scan |
| `ui/actions.lua:160-164` | `pcall(pack.update, ...)` → `utils.notify` on failure |
| `ui/actions.lua:194-199` | `pcall(pack.del, ...)` → `utils.notify` on failure |
| `loader/init.lua:336,344` | **bare `pcall`, result discarded** ← the outlier |

The loader is the exception, which suggests an oversight rather than a
design decision.

#### Risk

- Low. The change is local to the install path and does not touch the
  happy path.
- Retry semantics change: a plugin that fails to install will now be
  retried on the next trigger. That is the intent, but it means a
  permanently-bad `src` will retry on every trigger event. **Decide
  whether to cap retries** (e.g. keep a failure count per plugin and stop
  after N) or to rely on `once=true` being re-armed only on success.
  **Recommendation: re-arm the trigger only on success**, so a failed
  plugin is not retried on every `BufReadPre` — the user fixes their
  config and reloads.
- `utils.notify` defers through `vim.schedule`, so the notification is
  asynchronous. Do not rely on it having fired before the trigger returns.

#### Verification

- New test: a failing `vim.pack.add` produces an error notification naming
  the plugin.
- New test: a failed install does not mark the plugin loaded and does not
  set `replay_done`.
- New test: a failed install does not leave a `packadd` against a missing
  directory.
- Existing suite stays green (186 tests, 0 failed).

**Files:** `lua/resonance/loader/init.lua`, `test/behavior_spec.lua`

## Item 1 — Group the triggers in `triggers.lua`

**Why:** finding A. Ungrouped triggers are invisible to the `exclude` set
(finding C), so the replay's group-targeted firing cannot address them.
Grouping makes the exclusion mechanism meaningful and is defence in depth
against finding B recurring.

### Change

- `loader/triggers.lua`: create a dedicated augroup per plugin spec, e.g.
  `Resonance_<plugin_name>`, and pass `group = ...` to every
  `nvim_create_autocmd` the module registers (event, cmd, ft).
- Group names must be stable and unique per plugin so the replay's
  `exclude[group_name]` lookup resolves.

#### Risk

- The replay exclusion logic keys on group name. Changing group names
  changes what gets excluded. The existing regression tests must still pass
  unchanged — they are the guard.
- Grouping a trigger means `nvim_exec_autocmds` with an explicit `group`
  no longer fires it. Any code path relying on group-less firing must be
  audited.

#### Verification

- Existing suite: 186 tests, 0 failed.
- New test: a plugin's trigger is registered in a non-nil augroup.
- New test: the replay does not fire a grouped trigger that is excluded.

**Files:** `lua/resonance/loader/triggers.lua`, `test/behavior_spec.lua`

## Item 2 — Expose fired-event state so the config can skip already-fired buffers

**Why:** finding F. The loader already tracks which events fired per buffer
(`fired_events`, `loader/init.lua:65`, tracker group `ResonanceEventTracker`),
but that state is private, so the user's config re-fires events blindly.

### Change

- Add a public accessor on the loader, e.g.
  `M.has_fired(event, buf) -> boolean`, exported through
  `require('resonance.loader')`.
- The tracker already covers `BufReadPre`, `BufReadPost`, `BufNewFile`.
  `FileType` is not tracked — decide whether to add it or leave `FileType`
  re-firing as-is. **Leaning: add it**, because the duplicate `FileType` is
  the most user-visible half (treesitter attaches twice).
- Provide a helper that does the whole replay correctly, e.g.
  `M.replay_for_buffer(buf)`, so the config does not hand-roll the
  `exec_autocmds` calls. This keeps the fix in the plugin, not in the user's
  config.

#### Decision needed

Whether to expose a low-level `has_fired` predicate, or a high-level
`replay_for_buffer` that does the right thing. **Recommendation: both** —
the predicate for flexibility, the helper as the default path.

#### Config change (user side)

`~/.config/nvim/lua/config/resonance.lua:133-144` — replace the hand-rolled
loop with a call to the helper. This is a separate repo from resonance.nvim
and is edited in a separate session.

#### Verification

- New test: `has_fired` reports correctly after a native read.
- New test: `replay_for_buffer` does not re-fire an event that already ran.
- Manual: open a file, confirm treesitter attaches once (not twice).

**Files:** `lua/resonance/loader/init.lua`, `test/behavior_spec.lua`,
`~/.config/nvim/lua/config/resonance.lua` (separate repo)

## Item 3 — Check upstream snacks on the `nested = true` recursion

**Why:** finding G. Upstream snacks 2.31.0 still sets `nested = true` on its
event autocmd group (`lua/snacks/init.lua:189`).

### Status: reproduced, and the cause is confirmed

**Reproduced in isolation, without resonance.** A handler that reads a file
recurses to the 10-level nesting limit and Neovim raises E218:

| Handler flag | Result |
|--------------|--------|
| `nested = true` | **E218** — Autocommand nesting too deep |
| `nested = false` | ok, no error |

Reproducible across 4 consecutive runs.

**Resonance is not implicated.** The identical test with and without
`resonance.setup()` produces the same E218. The recursion is entirely
inside the snacks autocmd.

**Upstream status.** snacks 2.31.0 (released 2026-03-20) still has
`nested = true`; `lua/snacks/init.lua` has not been changed since. The
issue tracker has **no issue** for this — searched `E218`, `nesting too
deep`, `nested autocmd`, and `autocmd+E218`. The only hit (#2859) is a
closed dashboard-reload request that mentions E218 tangentially.

**Mechanism** (`autocmd.txt`, *autocmd-nested*): autocommands do not nest
by default. A `:e` inside an autocommand does not run the BufRead
autocommands. With `++nested` it does, and the nesting is limited to 10
levels to break recursive loops. snacks sets `nested = true` on the group
that loads its `bigfile`, `image`, `quickfile`, `indent`, `explorer`,
`words`, `dashboard`, `scroll`, `input`, `scope`, and `picker` plugins.
Any of those handlers that reads a file re-enters the read events.

#### Note on the probe method

`nvim_get_autocmds()` does **not** report the `nested` flag — it returns
`nil` for both `nested = true` and `nested = false`. A probe that infers
the flag from `get_autocmds` is invalid. The flag has to be varied in the
handler under test and the outcome compared.

#### Decision

- **Report upstream.** This is snacks' `nested = true`, and the fix is
  theirs: drop `nested`, or set it only on the handlers that genuinely need
  it. Reserving it per-plugin rather than for the whole group would keep
  the behavior that needs it without the recursion.
- **Do not patch snacks from the user config** unless upstream declines.
  Recreating the snacks augroup from a config file fights the next snacks
  release and is easy to get wrong.
- **No resonance.nvim change.** The recursion does not pass through
  resonance, and resonance's own replay is already bounded.

#### Verification

- The isolation reproduction above stays green as the reference case.
- If a workaround is adopted in the user config, verify the snacks plugins
  still load (bigfile, indent, picker) after the change.

## Item 4 — Convert remaining `vim.schedule` paths to `vim.async`

**Why:** `vim.async` is already used in `loader/build.lua` and
`ui/actions.lua`. The loader and scanner paths still use the older
`vim.schedule` + callback style. `vim.async` gives structured concurrency:
named tasks, cancellation on close, scoped child tasks.

### Stability note

`vim.async` is **new in Neovim 0.13** but carries **no experimental marker**
and is **not in `deprecated.txt`**. It is documented in `lua-async.txt`.
By contrast `vim.pack` *is* explicitly experimental (`pack.txt:211`). Since
resonance already targets 0.13+ (`README.md:3`), adopting `vim.async` costs
nothing in compatibility.

#### Candidates, in priority order

| Site | Current | Target | Outcome |
|------|---------|--------|---------|
| `ui/init.lua` deferred second `vim.pack.get({info=true})` pass | `vim.defer_fn` | cancellable task; dies when the UI closes | **done** |
| `loader/init.lua` `vim.pack.add` | blocking call | `async.wrap` on `vim.pack.add` | **not done** — see below |
| `scanner.lua` deferred info pass | `vim.schedule` | task with cancellation | **not done** — no such path exists |

#### What was done

The UI deferred pass now runs as a `vim.async` task. The close handler
cancels it, and the task checks that the UI is still open before it writes
into the state. The task handle lives in `st.state.details_task`.

UI open time: **9.5ms after, 10.4ms before** — no regression.

#### What was not done, and why

**`vim.pack.add` stays blocking.** `pack.add` is a synchronous call that
clones over git. Wrapping it in `async.wrap` would make the trigger
callback return before the install finishes, which changes the loader's
contract: `setup()` would run before the plugin is on disk, and the
install verification added in item 0 could not run. The trigger is
`once = true`, so the callback has to complete the install before the
trigger is consumed.

The blocking install is the correct behavior for a lazy loader — the
plugin must be ready when the trigger returns. Making it asynchronous
would be a design change, not a conversion.

**`scanner.lua` has no deferred pass.** The plan assumed one. The scanner
is a plain synchronous query; the deferred second pass lives in
`ui/init.lua`, which is where the conversion happened. The
`vim.schedule` calls in `ui/actions.lua` are already inside `async.run`
tasks, which is the correct pattern — they schedule work that has to
happen on the main loop, not long-running cancellable work.

#### Risk

- `vim.async` is brand new (0.13). API surface may still shift.
- Cancellation semantics differ from `vim.schedule`: a cancelled task must
  not write into UI state that has already been torn down. The task checks
  `st.state.buf` before it writes.
- Do **not** convert the hot paths. `vim.schedule` in a hot path is fine;
  the win is only for long-running cancellable work.

#### Verification

- Existing suite stays green (196 tests, 0 failed).
- New test: the deferred details pass runs as a task, and closing the UI
  cancels it without raising.
- Benchmark: UI open time must not regress — 9.5ms after, 10.4ms before.

**Files:** `lua/resonance/ui/init.lua`, `lua/resonance/ui/state.lua`,
`test/behavior_spec.lua`

## Sequencing

```text
0. Report install failures     (plugin change, smallest + highest impact)
1. Group the triggers          (plugin change, self-contained)
2. Expose fired-event state    (plugin change + config change)
3. snacks investigation         (research only, no plugin change)
4. vim.async conversion        (plugin change, largest blast radius)
```

Item 0 goes first: it is the smallest change and the highest impact — a
plugin that silently never loads is worse than any of the other issues
here. Items 1 and 2 are independent and can land in either order. Item 4 is
the largest and should follow 1-2 so any regression has a settled baseline.
