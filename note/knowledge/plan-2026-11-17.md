## Item 1 — Group the triggers in `triggers.lua`

**Why:** finding A. Ungrouped triggers are invisible to the `exclude` set
(finding C), so the replay's group-targeted firing cannot address them.
Grouping makes the exclusion mechanism meaningful and is defence in depth
against finding B recurring.

### Change

- `loader/triggers.lua`: create a dedicated augroup per plugin spec, e.g.
  `Resonance_<plugin_name>`, and pass `group = ...` to every
  `nvim_create_autocmd` the module registers (event, cmd, ft).
- Group names must be stable and unique per plugin so the replay's
  `exclude[group_name]` lookup resolves.

#### Risk

- The replay exclusion logic keys on group name. Changing group names
  changes what gets excluded. The existing regression tests must still pass
  unchanged — they are the guard.
- Grouping a trigger means `nvim_exec_autocmds` with an explicit `group`
  no longer fires it. Any code path relying on group-less firing must be
  audited.

#### Verification

- Existing suite: 186 tests, 0 failed.
- New test: a plugin's trigger is registered in a non-nil augroup.
- New test: the replay does not fire a grouped trigger that is excluded.

**Files:** `lua/resonance/loader/triggers.lua`, `test/behavior_spec.lua`

## Item 2 — Expose fired-event state so the config can skip already-fired buffers

**Why:** finding F. The loader already tracks which events fired per buffer
(`fired_events`, `loader/init.lua:65`, tracker group `ResonanceEventTracker`),
but that state is private, so the user's config re-fires events blindly.

### Change

- Add a public accessor on the loader, e.g.
  `M.has_fired(event, buf) -> boolean`, exported through
  `require('resonance.loader')`.
- The tracker already covers `BufReadPre`, `BufReadPost`, `BufNewFile`.
  `FileType` is not tracked — decide whether to add it or leave `FileType`
  re-firing as-is. **Leaning: add it**, because the duplicate `FileType` is
  the most user-visible half (treesitter attaches twice).
- Provide a helper that does the whole replay correctly, e.g.
  `M.replay_for_buffer(buf)`, so the config does not hand-roll the
  `exec_autocmds` calls. This keeps the fix in the plugin, not in the user's
  config.

#### Decision needed

Whether to expose a low-level `has_fired` predicate, or a high-level
`replay_for_buffer` that does the right thing. **Recommendation: both** —
the predicate for flexibility, the helper as the default path.

#### Config change (user side)

`~/.config/nvim/lua/config/resonance.lua:133-144` — replace the hand-rolled
loop with a call to the helper. This is a separate repo from resonance.nvim
and is edited in a separate session.

#### Verification

- New test: `has_fired` reports correctly after a native read.
- New test: `replay_for_buffer` does not re-fire an event that already ran.
- Manual: open a file, confirm treesitter attaches once (not twice).

**Files:** `lua/resonance/loader/init.lua`, `test/behavior_spec.lua`,
`~/.config/nvim/lua/config/resonance.lua` (separate repo)

## Item 4 — Convert remaining `vim.schedule` paths to `vim.async`

**Why:** `vim.async` is already used in `loader/build.lua` and
`ui/actions.lua`. The loader and scanner paths still use the older
`vim.schedule` + callback style. `vim.async` gives structured concurrency:
named tasks, cancellation on close, scoped child tasks.

### Stability note

`vim.async` is **new in Neovim 0.13** but carries **no experimental marker**
and is **not in `deprecated.txt`**. It is documented in `lua-async.txt`.
By contrast `vim.pack` *is* explicitly experimental (`pack.txt:211`). Since
resonance already targets 0.13+ (`README.md:3`), adopting `vim.async` costs
nothing in compatibility.

#### Candidates, in priority order

| Site | Current | Target |
|------|---------|--------|
| `ui/init.lua` deferred second `vim.pack.get({info=true})` pass | `vim.schedule` | cancellable task; dies when the UI closes |
| `loader/init.lua` `vim.pack.add` callbacks | callback style | `async.wrap` on `vim.pack.add` |
| `scanner.lua` deferred info pass | `vim.schedule` | task with cancellation |

#### Risk

- `vim.async` is brand new (0.13). API surface may still shift.
- Cancellation semantics differ from `vim.schedule`: a cancelled task must
  not write into UI state that has already been torn down. The UI already
  has a "closed" guard pattern — reuse it.
- Do **not** convert the hot paths. `vim.schedule` in a hot path is fine;
  the win is only for long-running cancellable work.

#### Verification

- Existing suite stays green.
- New test: closing the UI before the deferred info pass completes does not
  touch freed state (no error, no stale render).
- Benchmark: UI open time must not regress.

**Files:** `lua/resonance/ui/init.lua`, `lua/resonance/loader/init.lua`,
`lua/resonance/scanner.lua`, `test/behavior_spec.lua`

## Sequencing

```text
1. Group the triggers          (plugin change, self-contained)
2. Expose fired-event state    (plugin change + config change)
3. snacks investigation         (research only, no plugin change)
4. vim.async conversion        (plugin change, largest blast radius)
```

Items 1 and 2 are independent and can land in either order. Item 4 is the
largest and should follow 1-2 so any regression has a settled baseline.
